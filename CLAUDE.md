# Groove Work — Руководство по проекту

Здесь — текущая архитектура и правила. Историю изменений не ведём (для этого есть git и `data/changelog.json`): описываем «как есть», а не «как стало».

## Принципы разработки

1. **Простое лучше сложного.** Не плодим абстракции «на будущее». Три одинаковых строки лучше преждевременной фабрики.
2. **Оптимальность и эффективность важнее тормознутости.** Никаких N+1, лишних ререндеров, избыточных re-fetch.
3. **Расширяемость и масштабируемость важнее монолита.** Новый функционал — переиспользуемые блоки (composables, components, services, repositories), не однострочные хаки.
4. **Комментарии — только там, где они реально нужны.** Не описываем «что делает» очевидный код; «почему» — только если есть скрытый инвариант, обход бага или неочевидная мотивация.
5. **Профессиональный, лёгкий и краткий код.** Понятные имена, разумная декомпозиция, без раздувания.
6. **Только архитектура цветов и токенов.** Никаких `#hex` / `rgba()` в компонентах. Только `--color-*`, `--tag-*`, `--shadow-*`, `--radius-*` (см. «Цветовая система»).
7. **Дизайн един и согласован с тем, что уже есть.** Material 3 Expressive — стиль всего приложения. Не отклоняемся от стиля действующих экранов.
8. **При новых/переписываемых разделах — сначала ищем примеры лучших UI/UX подобного функционала в интернете** (ориентир — Material 3 Expressive от Google), и реализуем по образцу, адаптируя под проект.
9. **Дублирующиеся компоненты — выносим в общий.** Если используется в двух+ местах — `components/common/`, `composables/` или `utils/`. Без копипасты.
10. **Общение между микросервисами — ТОЛЬКО через gRPC.** Контракты в `api/proto`, стабы генерит `scripts/gen_proto.sh`. Никаких REST/HTTP-вызовов сервис→сервис. (REST микросервисов — только для клиентского трафика через nginx; Redis-каналы `gw2:<svc>:events` — только доставка сокет-событий клиентам через gatewaysvc, межсервисные вызовы через них не вести.)
11. **Сведения о выпуске (`data/changelog.json`) — НЕ ТРОГАТЬ без явной команды пользователя.** Истории версий платформа НЕ ведёт: файл описывает ТОЛЬКО текущий выпуск (`version`, `build`, `date`, `title`, `description`, `highlights`), их показывает раздел «Настройки → О приложении». Когда команда дана: никаких технических деталей, технологий и стека — только пользовательские последствия («стало быстрее, надёжнее и безопаснее»), кратко, в шуточном пользовательском тоне.
12. **CLAUDE.md — не помойка.** Здесь только актуальная архитектура и правила: историю версий сюда не писать, детали реализации оставлять коду и комментариям. Сюда — то, что нельзя вывести из кода за минуту: инварианты, границы ответственности, неочевидные решения.

## Что это

Groove Work — multi-tenant платформа учёта времени задач, аналитики и коллаборации. **Идентичность развязана с компаниями:** пользователь — самостоятельная сущность (регистрируется сам, не привязан ни к чему), может состоять в нескольких компаниях с разной ролью либо ни в одной (тогда ему доступны мессенджер/звонки/аккаунт/контакты). Внутри компании ведутся задачи/юниты, статистика, питомцы-грувики (лёгкая геймификация) и корпоративный портал; мессенджер, звонки, заметки, доски, ежедневники, напоминания и ИИ-ассистент — кросс-компанийные. Любой пользователь создаёт свою компанию и становится её администратором. Платформой управляет единственный супер-админ.

## Архитектура

Двадцать Go-микросервисов над общей PostgreSQL (схему ВСЕХ таблиц ведёт run-once контейнер `migrate` — goose, baseline + инкременты в `back-go/migrate/migrations`) + Redis + LiveKit. Python/Flask ликвидирован полностью.

- **gatewaysvc** (`gateway`, HTTP :8096) — realtime-шлюз: WebSocket `/ws`, комнаты `all`/`user_{id}`, presence в Redis, ринг-фаза звонков (WS-команды `call:*` → gRPC callsvc) и доставка событий ВСЕХ каналов `gw2:*:events` клиентам вербатим. Свой REST — только exact `GET /api/messenger/presence`. Готов к нескольким инстансам.
- **callsvc** (`calls`, HTTP :8090, gRPC :9090) — бизнес-логика звонков + LiveKit (токены/комнаты/вебхуки) + плашка звонка в чате (gRPC msgsvc: EnsureDialog, CreateCallMessage/GetCallMessage — fire-and-forget, плашка звонок не роняет). `calls.company_id` опционален: звонок возможен и между людьми без общей компании. Обратный канал клиентам — `gw2:calls:events`.
- **authsvc** (`auth`, HTTP :8091, gRPC :9091) — идентичность, авторизация, компании, членство, роли, реестр сессий и REST-бэкап. За токенами сюда никто не ходит — проверка локальная у всех; единственный gRPC — контракт владельца файлов (фото профиля) для раздела «Хранилище». Ручки — `/api/auth/*`, `/api/users/*` (в т.ч. `me/desktop` — личные настройки рабочего стола в JSONB `users.desktop_prefs`, непрозрачные для сервера), `/api/companies/*`, `/api/roles`, `/api/backup/*`.
  **Бэкап** (супер-админ) — УНИВЕРСАЛЬНЫЙ схемо-независимый дамп: таблицы обнаруживаются из БД на лету (`to_jsonb`/`jsonb_populate_recordset`), новые попадают в архив сами; денлист транзиентного/перегенерируемого (`email_verifications`, `password_resets`, `user_sessions`, `task_embeddings`, `note_embeddings`, `goose_db_version`). Импорт ДЕСТРУКТИВНЫЙ: TRUNCATE RESTART IDENTITY CASCADE + FK-топосортировка + setval (только по таблицам с колонкой `id` — на составных PK `pg_get_serial_sequence` роняет всю транзакцию), всё в одной транзакции. Разделы — `domain.BackupSections` ≡ `front/src/utils/backupSections.js` ≡ `backupSectionKeys` в apitest. **Раздел обязан перечислять ВСЕ свои таблицы**: TRUNCATE CASCADE вычистит забытую таблицу-спутник, а восстановить её будет неоткуда; таблица без раздела уезжает в псевдо-раздел `other` — это страховка от потери, а не место для новых таблиц. Сторожат `TestBackupSectionsCoverEveryTable` / `TestBackupExportCoversWholeSchema`.
- **msgsvc** (`messenger`, HTTP :8092, gRPC :9092) — мессенджер (см. раздел). gRPC-сервер: EnsureDialog/CreateCallMessage/GetCallMessage (callsvc), CreatePostMessage (portalsvc). Исходящий gRPC — `aisvc.SupportChat` (`AI_GRPC_ADDR`, пустой = ИИ выключен): **ИИ техподдержки** отвечает фоном на сообщения владельца dev-чата бот-сообщением `kind='system_dev_reply'`; молчит 15 мин после ответа человека, любая ошибка ИИ → прежний канированный автоответ раз в сутки. События → `gw2:messenger:events`.
- **aisvc** (`ai`, HTTP :8093, gRPC :9093) — LLM-шлюз, деловой ИИ-ассистент и ИИ-возможности разделов. **Ключ ОДИН — ПЛАТФОРМЕННЫЙ** (`ai_platform_settings`, Fernet `AI_KEY_ENCRYPTION_KEY`): ключ, адрес API, модели по умолчанию и каталог моделей с ценами задаёт супер-админ («Аудит платформы», `/api/ai/platform`). Ключей у компаний НЕТ; личный ключ пользователя — необязательная скрытая настройка (`user_ai_settings`): с ним запросы уходят на свой сервер и токены тарифа НЕ тратятся. **Тарификация — токены доступа** (баланс ведёт billingsvc): 1 токен = 1000 токенов самой дешёвой модели каталога, остальные дороже пропорционально `ai_models.price_per_mtok` (округление вверх, бесплатных обращений нет). Порядок: `CheckAI` до запроса, `ConsumeAI` с фактическим расходом после. Сколько токенов выдаётся — решает billingsvc; в 7.0 это 1000 в сутки каждому (см. ниже). **Выбор модели временно закрыт** (`domain.ModelChoiceLocked`): на платформенном ключе все работают на модели платформы, настройки отдают флаг `model_locked`. На СВОЁМ ключе выбор остаётся — там платит сам пользователь. Платит: личные функции — сам пользователь, компанийные — СОЗДАТЕЛЬ компании и только если разрешил (`companies.ai_shared`). **Возможности включаются по отдельности**: личные — Hola-ассистент и ИИ в заметках, компанийные — умный поиск задач (выключен или нет токенов → tasksvc падает на текстовый поиск) и факты ТВ-режима. gRPC: Status/Chat/Embed/SemanticSearch/ReindexTask + SupportChat (на платформенном ключе со своей моделью, токены пользователей не тратит). Исходящий gRPC — tasksvc (инструменты статистики ассистента) и billingsvc (учёт токенов).
- **tasksvc** (`tasks`, HTTP :8095, gRPC :9095) — ядро платформы: задачи (избранное, личные цвета, теги, комментарии, ответственный/этап), юниты (1 активный на пользователя), типы юнитов, этапы, отделы, статистика (+ xlsx-экспорт на excelize) и вся YouGile-интеграция (см. раздел). REST `/api/tasks|units|unit-types|departments|stages|stats|yougile`.
  **Теги задач** — справочник компании (`tags`, цвет из палитры `--tag-*`) + `task_tags`; CRUD справочника — менеджер, назначение задаче — сотрудник; роуты ПОД `/api/tasks/tags` (отдельный префикс потребовал бы правок nginx/vite; с `/:id<int>` не конфликтует). Теги ОБЩИЕ для компании — входят в `TaskBroadcast`, в отличие от личного `color`. Фильтры `?tag_ids=`, `?colors=` — обычные предикаты, совместимы с семантическим поиском.
  **Новые комментарии** — `task_comment_seen`: список комментариев возвращает `{items, new_count}`, `POST …/comments/seen` гасит бейдж.
  **Поиск**: текстовый (регистр не важен; запрос с метасимволами и валидным синтаксисом идёт как РЕГУЛЯРНОЕ выражение, оператор `~*`) плюс семантика aisvc, если ИИ включён — она ДОПОЛНЯЕТ выдачу, поэтому только что созданная задача находится по названию ещё до расчёта эмбеддинга.
  gRPC-сервер: `tasks.v1.TasksService` — статистика и `GetTaskLink` для ИИ-ассистента + голосовые операции для alicesvc (`department_id`/`unit_type_id == 0` — автовыбор единственного, иначе DEPARTMENT_REQUIRED/UNIT_TYPE_REQUIRED для уточняющего вопроса). Исходящий gRPC — хуки petsvc (fire-and-forget). События → `gw2:tasks:events`.
- **petsvc** (`pets`, HTTP :8094, gRPC :9094) — питомцы-грувики (см. раздел), чистая гейм-механика без ИИ. gRPC-сервер — хуки доменных событий tasksvc. Исходящих вызовов нет. События → `gw2:pets:events`; фоновый цикл заботы внутри.
- **portalsvc** (`portal`, HTTP :8102) — корпоративный портал (см. раздел). Своего gRPC-сервера нет; исходящий — CreatePostMessage в msgsvc. События → `gw2:portal:events`.
- **pushsvc** (`push`, HTTP :8097) — FCM HTTP v1 (Android), токены устройств в `device_tokens`. Подписан на `gw2:messenger:events` (message:new), `gw2:tasks:events` (task:created → ответственному), `gw2:gateway:events` (call:incoming, high-priority), `gw2:portal:events` (post:new), `gw2:reminder:events` (reminder:fire) и `gw2:pets:events` (kudos:received, pet:sick/pet:runaway). Шлёт ТОЛЬКО офлайн-получателям (presence) — приложение на переднем плане получает событие по WS. Мёртвые токены чистятся по ответу FCM. Без `FIREBASE_CREDENTIALS_JSON` отправка отключена.
- **registrysvc** (`registry`, HTTP :8099) — реестры: настраиваемые компанией таблицы-справочники. Набор полей (9 типов: image/file/text/number/checkbox/select/link/datetime/stock + раскладка `col_span`/`row_span` в 3-колоночной сетке) и записи; числовое поле принимает ТОЛЬКО число (буквы в нём роняли сортировку: она приводит значение к numeric) с необязательными границами `min`/`max`, а `stock` («Наличие») хранит `{taken, until}` — пустое значение означает «на месте»; значения — `registry_records.data` (JSONB по строковому id поля) + производное `search_text` (ILIKE, триграммный GIN). Структуру правит администратор компании (удаление поля чистит его данные и файлы), записи ведёт любой участник; экспорт xlsx. Картинка при загрузке получает **миниатюру** (`pkg/records.Thumbnail` — стандартная библиотека, box-фильтр; JPEG, а при полупрозрачности PNG): ключ кладётся в `thumb` рядом с `path`, её показывает таблица записей. Миниатюры нет у мелких картинок и у нечитаемых форматов (webp) — тогда показывается оригинал; удаляются и чистятся оба ключа (`filePaths`), включая осиротевшие после замены значения. **Внешние ссылки** — код-capability в `registry_shares` с уровнем `access` (`view` — просмотр и выгрузка, `edit` — плюс создание и правка записей): публичные `GET /api/registries/shared/:code{,/records,/export}` и, для `edit`, `POST/PATCH …/records` и `POST …/uploads` (auth-мидлварь монтируется на префикс и пропускает `shared/*`; уровень проверяет сервис). Автора у записи по ссылке нет (`created_by` пуст), место тратится из квоты компании-владельца, события идут в её комнату. Фронт-роут `/registry/:code` — самостоятельная страница (`meta.fullscreen`, иначе вошедший увидел бы пустой рабочий стол), собранная из ТЕХ ЖЕ компонентов, что и раздел (`components/registry/RegistryRecords|RegistryRecordDialog|RegistryExportDialog|RegistryColumnsDialog`, `composables/useRegistryColumns|useRowSelection`). Скоуп — активная компания из токена, межсервисных вызовов нет. События → `gw2:registry:events`.
- **calendarsvc** (`calendar`, HTTP :8100) — календари: близнец registrysvc (те же типы полей и раскладка) с отличиями: у записи есть встроенное обязательное «Дата и время» без секунд (колонка `event_at`, не входит в `calendar_fields`), а поля поддерживают **условную видимость** (`visible_field_id`/`visible_value` — вычисляется на фронте, скрытые поля не сохраняются) и два независимых флага `show_in_table` / `show_in_card`. Записи выбираются диапазоном дат (день/неделя/месяц), экспорт xlsx за период. `GET /api/calendars/agenda` — ближайшие события ВСЕХ календарей компании (живая плитка): один SQL + батч полей, заголовок карточки считает сервер по первому полю `show_in_table` (зеркало `utils/calendarFields.js:entryTitle`). Внешние ссылки — как у реестров (`/calendar/:code`). События → `gw2:calendar:events`.
- **diarysvc** (`diary`, HTTP :8101, gRPC :9101) — личные ежедневники: записи-задачи, привязанные к дню. Принадлежит ОДНОМУ пользователю (`diaries.owner_id`), НЕ зависит от компании, набор полей карточки ФИКСИРОВАННЫЙ (день, опц. время начала/конца в минутах от полуночи, название, описание, `done` → архив, связь `linked_task_id`). Запись можно отметить выполненной, перенести drag-and-drop'ом на другой день и/или в другой свой ежедневник и привязать к ней задачу+юнит. `GET /api/diaries/agenda` — невыполненные дела всех доступных ежедневников за период (один SQL с JOIN и `count(*) OVER ()`, границы дня считает клиент — его зоны сервер не знает). **Шаринг**: публичной ссылкой (read-only, `/diary/:code`) и адресно пользователю (`diary_user_shares`, `{user_id, can_check}`): адресат видит ежедневник во вкладке «Поделились» и при `can_check` может отмечать записи (сценарий «руководитель раздаёт задачи»), но не редактировать. gRPC — голосовые операции alicesvc. События (`diary:*`, `diary_entry:*` — с префиксом, чтобы не пересечься с `entry:*` календаря) → `gw2:diary:events`, адресуются владельцу и адресатам.
- **notesvc** (`notes`, HTTP :8103, gRPC :9103) — личные заметки: rich-текст TipTap в JSONB `notes.doc`, `text_content` — плоский текст, пересчитывается сервером при каждом сохранении (поиск ILIKE по триграммному GIN, txt/docx-экспорт). **Иерархические папки** (`note_folders`, заметка — в РОВНО одной папке): защита от циклов recursive-CTE, удаление папки РЕПАРЕНТИТ детей в родителя, copy — глубокая копия поддерева. **Теги-метки** (`note_tags`/`note_tag_items`, цвет из `--tag-*`). Закрепление, публичные ссылки (`note_shares`, `access IN (view, edit)`, фронт `/note/:code`). **Адресный шаринг ЗАМЕТОК И ПАПОК — пользователю или компании** (доступ по расшаренной папке КАСКАДИТ на поддерево; членство `user_companies` читается напрямую из БД). **Эффективный доступ считает сервер** (`NoteAccess`/`FolderAccess`, recursive-CTE подъём по `parent_id`): лучший из owner|edit|view с учётом прямых шар и папок-предков, `my_access` в ответах. **Совместное редактирование** — `POST /:id/collab {kind: join|leave|cursor|doc}`, броадкаст всей аудитории. Экспорт txt/docx и zip поддерева, импорт .txt/.docx (`internal/docx` — свой парсер и генератор, без внешних зависимостей). **ИИ-поиск**: при глобальном поиске и включённом ИИ — семантический через ЕДИНСТВЕННЫЙ исходящий gRPC `aisvc.Embed` (векторы хранит сам notesvc, fail-open на пословный текстовый поиск); поиск всегда ГЛОБАЛЬНЫЙ (фильтр папки снимается, подмешиваются расшаренные). Хендлеры зовут сервис НАПРЯМУЮ (без endpoint-обёрток). События → `gw2:notes:events`, адресуются поимённо всей аудитории, без комнаты `all`.
- **drivesvc** (`drive`, HTTP :8108, gRPC :9108) — «Диск»: личное файловое хранилище. По устройству близнец notesvc и boardsvc (владелец один, компания ни при чём, доступ выдаётся шарингом), но предмет — сам файл: `drive_files.storage_key` указывает на объект в `pkg/storage`, наружу отдаётся адрес `/uploads/<key>`. **Папки** `drive_folders` (дерево по `parent_id`, перенос защищён от циклов проверкой поддерева), **корзина** — `deleted_at` у файла и папки: удаление папки уводит в корзину ВСЁ её поддерево вместе с файлами, место при этом остаётся занятым (пока файл можно вернуть, он никуда не делся), а пролежавшее дольше `TrashKeepDays`=30 чистит фоновый цикл сервиса. Избранное (`starred`), вкладки «Недавние» и «Поделились со мной». **Шаринг** — публичные ссылки (`drive_shares`, фронт `/drive/s/:code`) и адресная выдача человеку или компании (`drive_user_shares`), доступ по папке КАСКАДИТ на поддерево; эффективный уровень считает сервер (`FileAccess`/`FolderAccess`, recursive-CTE подъём по `parent_id`). Загрузка идёт через `SaveFor` — файл сверх квоты не сохраняется вовсе. Единственный gRPC — контракт владельца файлов для раздела «Настройки → Хранилище». События → `gw2:drive:events`, поимённо аудитории.
- **boardsvc** (`board`, HTTP :8105) — личные доски рисования: **сцена холста** (`boards.scene` JSONB, версия 2: `layers` + плоский список объектов — перо/маркер, линии и стрелки, фигуры, надписи, стикеры, картинки и булавки-комментарии с ветками ответов; `text_content` для поиска пересчитывается сервером; `preview_path` — миниатюру снимает клиент). **Слои**: порядок = порядок отрисовки, `visible` прячет слой целиком (скрытое не попадает и в выгрузку), `locked` запрещает правку; `group` связывает объекты. Сцены версии 1 поднимаются на лету (`ParseScene` ≡ `normalizeScene` на фронте). По устройству — **близнец notesvc**: те же папки, закрепление, архив, публичные ссылки, адресный шаринг досок И папок с каскадом по папке, `BoardAccess`/`FolderAccess`. Отличия: **нет тегов** (организация — только папки) и **нет ИИ-поиска и gRPC** (межсервисных вызовов нет вовсе). **Выгрузка**: SVG/JSON/zip строит сервер (картинки встраиваются data-URI, ключ хранилища достаётся из адреса `/uploads/<key>`), PNG/JPG/PDF собирает клиент (`utils/boardExport.js` — свой минимальный PDF, генератор в бандл не тащим). Цвет объекта хранится КЛЮЧОМ палитры, а не hex: доска следует теме, конкретные значения нужны только SVG-экспорту (файл уезжает наружу — исключение как в шаблонах писем). **Совместная работа**: горячий путь — `ops` с ПООБЪЕКТНЫМИ правками (соавторы применяют адресно, поэтому работа над разными объектами не затирает чужие штрихи; сервер их не разбирает); целую сцену шлём только на структурные изменения и применяем как LWW, кроме момента чужого жеста. События → `gw2:board:events`, поимённо аудитории.
- **remindersvc** (`reminder`, HTTP :8106) — личные напоминания: разовые и повторяющиеся (`daily`/`weekdays`/`weekly`/`monthly`/`yearly`, «каждые N», необязательный конец), со свободным текстом либо **привязкой** к записи ежедневника/календаря (снимок названия и «за сколько минут до»; снимок актуализирует раздел, который правит запись, — межсервисных вызовов нет). Времена в БД — UTC, `timezone` (IANA) нужен повторам: «каждый день в 9:00» остаётся девятью утра и после перевода часов; месяц с 31-м числом клампится к последнему дню. **Планировщик** внутри сервиса (тик 30 с): `ClaimDue` атомарно забирает наступившие сроки (`FOR UPDATE SKIP LOCKED … RETURNING`) — отсюда «одно срабатывание — одна доставка» при нескольких инстансах; следующий срок считается ОТ ТЕКУЩЕГО МОМЕНТА, поэтому после простоя не бывает пачки пропущенных уведомлений. События → `gw2:reminder:events` (`reminder:fire` — тост, системное уведомление и звук; pushsvc шлёт офлайн-пуш).
- **alicesvc** (`alice`, HTTP :8104) — голосовой навык Алисы. Публичный вебхук `POST /api/alice/webhook`: авторизации в мидлварях нет, PASETO-токен приходит в теле (связка аккаунтов) и проверяется локально; нет токена → директива `start_account_linking`. Состояния НЕТ (ни БД, ни Redis): мультиход диалога живёт в `session_state` Диалогов. **Разбор фраз ИИ-first** — gRPC `aisvc.Chat` (промпт-экстрактор интентов → JSON, бюджет 3 с), fail-open на регэксп-парсер `internal/service/parser.go` (он же единственный путь без ИИ; уточняющие «да/нет/номер» разбираются всегда без ИИ). Даты — в таймзоне `meta.timezone`. Операции — ТОЛЬКО gRPC владельцев: tasksvc, diarysvc, notesvc. Регистрация — консоль Яндекс.Диалогов (Webhook URL `https://<домен>/api/alice/webhook`, авторизация `/oauth/authorize`, токен `/api/auth/oauth/token`, креды `OAUTH_ALICE_CLIENT_ID/SECRET`).
- **billingsvc** (`billing`, HTTP :8107, gRPC :9107) — подписки, магазин и платежи. **Подписка принадлежит ПОЛЬЗОВАТЕЛЮ, компания наследует тариф своего СОЗДАТЕЛЯ.** Линейка «Джун / Мидл / Синьор»: ЛИМИТЫ конечны и живут в коде (`domain.PlanLimits`), ЦЕНЫ правит супер-админ (`billing_plans`). Докупки складываются с лимитами (место, пачка токенов, компания, место сотрудника В КОНКРЕТНУЮ компанию). Заказ применяется РОВНО ОДИН РАЗ (`applied_at` в WHERE) — повторный вебхук ничего не удваивает. Платёжный шлюз — порт `domain.PaymentProvider` с реализацией `manual` (счёт подтверждает супер-админ); подключение банка = новый файл в `internal/payments` + строка в фабрике, сервис и фронт не меняются. Промокоды: `percent`/`amount` — скидка, `days`/`tokens` — подарок. Токены ИИ: квота обновляется ЛЕНИВО по `period_end`, списание атомарно (сначала квота, потом докупленное), read-путь баланс НЕ пишет. **Хранилище** — счётчик `billing_storage_usage` (быстрая сумма для лимитов) плюс **журнал файлов** `billing_storage_files`, из которого живёт раздел «Настройки → Хранилище». Владельцы файлов сообщают о них через `TrackStorage` (`pkg/records.FileStore.SaveFor` проверяет остаток ДО записи), а **занятое место считает сам биллинг**: размеры добавленных приходят в запросе, размеры удалённых он знает из журнала — поэтому мерить объекты в S3 перед удалением не нужно. Файл компании тратит квоту её создателя, и `user_id` журнала — всегда ВЛАДЕЛЕЦ КВОТЫ. Планировщик продлений: истёкшая подписка снимается (строки нет = «Джун»). gRPC: GetEntitlements/CheckStorage/TrackStorage/CheckAI/ConsumeAI/LogAction.
  **В выпуске 7.0 подписки СКРЫТЫ от пользователя** (оплата не подключена) — механика цела, скрыт вход в неё. Переключатель — `domain.SubscriptionsHidden` (+ парный `SUBSCRIPTIONS_VISIBLE` во фронтовом `utils/release.js`). Пока он включён: `EffectiveLimits` снимает ВСЕ счётные лимиты и открывает платные возможности (иначе человек упирался бы в бесплатного «Джуна» без возможности купить выход), а токены ИИ выдаются всем поровну — `DailyAITokens` = 1000 в сутки, период кончается в московскую полночь (`AIQuota`; длину периода задаёт домен, а не SQL). Тарифная линейка `PlanLimits` не тронута и вернётся вместе с оплатой; тесты, проверяющие действие лимитов, загейчены по флагу. Идентичность читает НАПРЯМУЮ из общей БД read-only. Публичный вебхук `/api/billing/webhook/payments`, админские ручки под `/api/billing/admin/*`.
- **mailsvc** (`mail`, gRPC :9098, HTTP :8098 только `/healthz`) — рассылка писем: `mail.v1.MailService.Send {to, to_name, template, params}` рендерит брендированный HTML-шаблон и шлёт по SMTP. Stateless. Зовёт его authsvc. В dev письма ловит `mailpit` (UI :8025). Наружу не торчит. Шаблоны — исключение из правила токенов: инлайн-CSS с хардкодом цветов бренда (почтовые клиенты не понимают CSS-переменные).

**Слои Go-микросервисов (одинаковые):** `internal/domain` (модели, порты, ошибки) → `internal/service` (бизнес-логика на портах, тестируется фейками) → `internal/repository/...` (pgx, raw SQL; redis) → `internal/transport/...` (Fiber / gRPC) + `internal/endpoint` (go-kit обёртки use-case'ов; в notesvc и boardsvc их нет — хендлеры зовут сервис напрямую). Формат ошибок REST: `{"error": CODE, "message": ...}` + HTTP-статус (исторический формат REST звонков — ключ `"code"`). Логи — slog JSON.

**Общий модуль `back-go/pkg`** (`replace ../pkg` в go.mod каждого сервиса): `pasetoauth` (Verifier + мидлвари RequireAuth/RequireToken/RequireRole/RequireSuperAdmin/OptionalUserID; claims — `is_super_admin` + опциональный контекст активной компании; `RequireRole` требует активную компанию, супер-админ в неё не проходит), `apierror` (`Error{Code, Message, HTTPStatus, Extra}` + `Respond`; доменные `errors.go` сервисов — алиасы на него), `events` (публикатор `gw2:<svc>:events`), `marshform`, `bootstrap` (env, slog, pgx/redis, graceful shutdown через `Run(Component...)`), `httpserver` (общий Fiber-сетап ВСЕХ сервисов: recover + сквозной `X-Request-ID` + стандартный `/healthz`), `records` (ядро «настраиваемых записей» реестров/календарей: типы полей, валидация значений, `SearchText`, `NormalizeSpans`, `NewShareCode`, параметризуемый `FileStore(subdir)`), `storage` (бэкенды local/s3, фабрика `FromEnv`; ключ объекта = относительный путь `<svc>/...`; в S3 объекты грузятся с `public-read` ACL — ключ Beget не имеет прав на политику бакета — и запись СРАЗУ сверяется HeadObject'ом: хранилище отвечало «успех», не сохранив объект, и карточка навсегда ссылалась на пустоту; миграция файлов — `pkg/cmd/uploadmigrate`), `gen/<svc>pb` — ЕДИНСТВЕННОЕ место сгенерированных стабов (их импортируют и владелец, и клиенты — без перекрёстных module-зависимостей). **В pkg только инфраструктура — домен туда не выносить.**

**Маршрутизация (nginx и vite-proxy, порядок важен — длинные префиксы раньше `/api/`):** `/api/calls/` → 8090; `/api/auth`, `/api/users`, `/api/roles`, `/api/backup`, `/api/companies` (БЕЗ хвостового слэша) → 8091; regex `^/api/companies/\d+/ai-settings` → 8093 (regex-location выигрывает у префикса; в vite regex-ключ стоит раньше); `/api/ai` → 8093; exact `/api/messenger/presence` → 8096, остальной `/api/messenger` → 8092; `/api/pets` → 8094; `/api/tasks|units|unit-types|departments|stages|stats|yougile` → 8095 (вебхук YouGile — без авторизации); `/api/push` → 8097; `/api/registries` → 8099; `/api/calendars` → 8100; `/api/diaries` → 8101; `/api/portal` → 8102; `/api/notes` → 8103; `/api/alice` → 8104 (публичный вебхук); `/api/boards` → 8105; `/api/drive` → 8108 (загрузка до 500 МБ); `/api/reminders` → 8106; `/api/billing` → 8107 (публичный вебхук платежей); exact `/api/changelog` — статика (в dev — vite-плагин); незнакомый `/api/*` — 404 от nginx; `/ws` → 8096 (в dev фронт ходит на `ws://<хост-страницы>:8096/ws` — хост из адреса страницы, чтобы работал заход с других устройств сети); `/uploads/<key>` — в dev с диска, в prod проксируется на публично-читаемый S3-бакет (контракт единый, клиенты бэкенд не различают); `/apps/` — статика: `/apps/mobile/` (APK обёртки + version.json), `/apps/groovework.apk` + `/apps/version.json` (зеркало для прежних нативных установок), `/apps/desktop/`; `/livekit/` → LiveKit. Фронт ходит только на относительные пути.

## Авторизация (PASETO + authsvc)

- **Access-токен** — PASETO v4.public (Ed25519, 15 мин): подписывает только authsvc (`PASETO_PRIVATE_KEY`), остальные проверяют по `PASETO_PUBLIC_KEY`. Скомпрометированный сервис-верификатор не может выпустить токен.
- **Refresh-токен** — v4.local (`PASETO_REFRESH_KEY`, 30 дней), cookie `refresh_token` (HttpOnly, Secure, SameSite=Strict), читает только authsvc. Несёт `session_id` — строку реестра входов, поэтому вход отзываем: refresh отозванной сессии → 401.
- **Клеймы:** sub, type, exp/iat, force_change, is_super_admin и ОПЦИОНАЛЬНЫЙ контекст активной компании (company_id, company_name, company_settings, role_level). «Нет активной компании» — НОРМАЛЬНОЕ состояние, а не признак админа. Супер-админ — отдельный флаг, не роль.
- **Регистрация публичная с подтверждением email:** `POST /api/auth/register` создаёт `email_verified=FALSE`, пишет код+токен в `email_verifications` и шлёт письмо; ответ `{status:"verification_required"}` — сессии нет. Логин предлагается транслитом из ФИО (`/api/auth/suggest-login`), пароль генерит клиент. Подтверждение — `/api/auth/verify-email` (`{token}` из ссылки или `{email, code}`) → выдаёт сессию. Переотправка — троттл 60 с. Логин неподтверждённого → 403 `EMAIL_NOT_VERIFIED`. Сотрудники, заведённые администратором, считаются подтверждёнными (у них force-change). Login при 0 компаний не падает; 1 компания — автоактивна; >1 — login-gate.
- **Сброс пароля:** `forgot-password` (ответ всегда ok — аккаунт не раскрываем, троттл 60 с) → токен в `password_resets` + письмо; `reset-password` меняет пароль и возвращает `{login}` (фронт ведёт на вход без автологина).
- **force_change:** `is_default_pass=TRUE` → клейм `force_change`, все API отвечают 403 `FORCE_PASSWORD_CHANGE`, кроме `change-default` и logout. Дефолтный пароль — `<login>123`; меняется ТОЛЬКО пароль (новый логин необязателен).
- **Компании:** маршруты `/companies` (супер-админ — все, обычный — где он администратор/создатель) и `/companies/:id` (`CompanyManageView`: Обзор/Участники/Настройки/Опасная зона). Настройки компании (ИИ, выходные, режим питомцев, ссылка-приглашение, фичи, YouGile) живут здесь, а не в «Настройках». **Управление участниками/ролями, создание сотрудников и удаление компании — только СОЗДАТЕЛЬ (`companies.created_by`) или супер-админ** (`creatorAuthority`); не-создатель-администратор видит компанию и правит настройки, но участниками не управляет (`companyAuthority`). **Приглашения** двумя путями: ссылка-код `/join/:code` (роль Сотрудник) и email-инвайт с ролью (`company_invites`, письмо, `/invite/:token` → членство + сессия).
- **Фронт токен НЕ декодирует** — authsvc дублирует клеймы в телах register/login/refresh/change-default; стор кладёт их в `claims` (`applySession`), client.js обновляет при каждом refresh. 401 → очередь запросов + refresh + повтор.
- **OAuth-провайдер (связка аккаунтов Алисы):** страница согласия `/oauth/authorize` → `POST /api/auth/oauth/authorize` (одноразовый код в Redis, TTL 10 мин) → публичный `POST /api/auth/oauth/token` (`authorization_code`/`refresh_token`, ошибки — коды RFC 6749). redirect_uri ограничен `https://social.yandex.net/broker/redirect`; пустые креды — эндпоинты отвечают отказом.
- **Вход через Яндекс ID** (мы — OAuth-клиент): кнопка видна только при настроенных `YANDEX_OAUTH_CLIENT_ID/SECRET`; возврат на `/yandex-callback` → `POST /api/auth/yandex/callback`: матчинг по `users.yandex_id`, затем по email (привязка + `email_verified=TRUE` — почта подтверждена Яндексом), иначе автосоздание аккаунта (ФИО, логин транслитом, случайный пароль, телефон и аватарка профиля). Нужны scopes login:email, login:info, login:avatar, login:default_phone.
- **Аватар**: загруженное фото (`users.avatar_path`), эмодзи-значок (`users.avatar_emoji`) или автоматический identicon — в этом порядке приоритета. Значок и identicon отдаёт ОДНА ручка `GET /api/users/<id>/identicon` (значок — SVG: цветные эмодзи рисует шрифт системы, своего эмодзи-шрифта серверу не нужно), поэтому выбор виден всюду, где показывается аватар, без правок в интерфейсе. Ответ идёт с `Cache-Control: no-cache` — адрес постоянный, а картинка за ним меняется.
- **Смена пароля обрывает ПРОЧИЕ сеансы** (`RevokeOtherSessions`, текущий остаётся): иначе устройство, с которого пароль утёк, обновляло бы токен ещё месяц. Та же операция — за кнопкой «Выйти на всех устройствах» в аккаунте.
- **«Аккаунт» — панель НАСТРОЕК** (`components/settings/AccountSection.vue`), самостоятельного раздела «Профиль» нет (`/profile` — редирект на `/settings?section=account`). Три блока: карточка идентичности (аватар-плитка → `ImageLightbox`, имя, должность, контакты-пилюли), ряд пилюль «подписка и внешние аккаунты» (подписка из billingsvc → магазин; Яндекс-аккаунт; YouGile) и «Авторизация и сессии» (плитка QR/ТВ-кода + карточки входов). Редактирование данных — `components/profile/ProfileEditDialog.vue`. Плюс тумблер «Я в отпуске» — свой отпуск в АКТИВНОЙ компании (строки нет, пока активной не выбрано; подпись всегда называет компанию — в другой человек продолжает работать). Личной статистики здесь нет.
- **Сессии и устройства** (`user_sessions`): каждая выданная пара принадлежит строке реестра, её id зашит в refresh. Карточка опознаётся по User-Agent (`domain.DescribeUserAgent`), адрес — из `X-Forwarded-For`/`X-Real-IP`, `last_seen_at` двигает сам refresh. `GET /api/auth/sessions` (текущий помечен по cookie), `DELETE …/:id` (чужой id не найдётся — `user_id` в условии UPDATE); logout гасит свой сеанс. Перевыпуск пары в ТОЙ ЖЕ сессии (смена компании, change-default, refresh-грант) карточки не плодит. Токены до реестра (`session_id == 0`) работают и получают карточку при первом refresh. Весь реестр **fail-open**. Город в чипе — внешний гео-сервис (`GEOIP_URL` с подстановками `{ip}`/`{token}`, кэш Redis 30 дней, резолв асинхронный — логин сеть не ждёт; пустой URL выключает гео).
- **Брутфорс-щит** (Redis): после каждых 5 неудач блокировка 10·2^(n−1) секунд, 429 с `retry_after_sec`, фронт показывает таймер. Redis недоступен → fail-open. Регистраций с одного адреса — 8 в час; `REGISTER_IP_LIMIT` поднимает потолок и нужен ТОЛЬКО испытательным стендам (сотни аккаунтов с 127.0.0.1 — их обычный режим), в проде переменную не задавать.
- **Пароли** — pgcrypto: `crypt(pw, gen_salt('bf'))`.
- **Аватарки** — общий uploads (`avatars/`); `avatar_path = NULL` → identicon `GET /api/users/<id>/identicon` (PNG 8×8 от sha256(id)).
- **Dev-ключи PASETO** захардкожены синхронно в `dev.sh`, `Makefile`, `deploy/docker-compose.override.yml`. Прод-ключи генерирует `deploy_server.sh` (пара Ed25519 целиком).
- Все api-модули `front/src/api/*.js` ведутся вручную (Swagger сервисы не публикуют).

## Система прав (идентичность развязана с компаниями)

**Пользователь — самостоятельная сущность** (`users`: только идентичность, `is_active`, `is_super_admin`). Он НЕ знает про компании. Принадлежность и роль живут ТОЛЬКО в `user_companies (user_id, company_id, role_id, post)`. Один аккаунт — во многих компаниях с разной ролью.

**Личная компания**: аккаунт без единого членства получает свою («Фамилия Имя — личное», создатель = он сам, роль администратора) — заводит её `startSession` при входе, существующим раздала миграция 00076. Причина: к компании привязана вся работа (задачи, юниты, статистика, реестры, календари, портал), и без неё человек попадал в приложение, где половина разделов просит выбрать компанию. Супер-админ исключён. При этом «нет компании» остаётся ВАЛИДНЫМ состоянием (членство отзывают, компанию удаляют) — проверки нигде не сняты.

**Три роли В КОМПАНИИ** (фиксированы в БД, создавать/удалять нельзя; `domain.Level*`, фронт — `composables/usePermission.js`):

| Уровень | Роль | Особенности |
|---|---|---|
| 1 | Сотрудник (EMPLOYEE) | базовая работа с задачами/юнитами |
| 2 | Менеджер (MANAGER) | +управление чужими юнитами, отделы/типы юнитов, экспорт статистики |
| 3 | Администратор (ADMIN) | +управление компанией: настройки, члены, инвайт, CRUD сотрудников |

**Супер-админ — отдельный класс** (`users.is_super_admin`, бутстрап — `reset_superadmin_password.sh`): видит все компании и всех пользователей, управляет компаниями, но к компанийному контенту (задачи, грувики, YouGile, статистика) доступа НЕ имеет. Не роль и `RequireRole` не проходит.

**Активная компания** сессии — в access-токене; переключение — `switch-company`. Хака `?company_id=` для админа НЕТ. Отключённая компания → 403 `COMPANY_DISABLED`.

**Гарды управления** (`back-go/auth/internal/service`): роль не выше своей (равную — можно); супер-админа изменять нельзя; защита «последнего администратора компании». Создатель компании автоматически получает членство-администратора.

## Ключевые бизнес-правила

- У пользователя единовременно только 1 активный юнит (`datetime_end IS NULL`); нельзя архивировать задачу с активным юнитом.
- Удаление типа юнита каскадно удаляет все юниты с этим типом.
- Цвет задачи индивидуален (`user_task_colors`); в броадкастах `task:created/updated` поле `color` вырезается, чтобы чужие клиенты не перезаписали свой.
- **Компанийные сущности не выходят за компанию.** Прямая ссылка на задачу: постороннему — 403 `TASK_FORBIDDEN`, сотруднику той же компании с ДРУГОЙ активной — 409 `TASK_OTHER_COMPANY` с `company_id` в extra (фронт предлагает переключиться), несуществующей — 404; мутации остаются глухими 404 — существование чужих задач не раскрываем. Гость уходит на `/welcome?redirect=…` и возвращается после входа.
- Собственные действия на фронте — оптимистичные обновления стора; сокет-события дублируют их для остальных (handlers идемпотентны). **Никогда не пушить вслепую результат create в список: сокет-событие может прийти раньше HTTP-ответа** — и оптимизм, и сокет идут через один upsert по id.
- **Режим «в отпуске»** (`user_companies.on_vacation`) — **company-scoped**: в одной компании человек отдыхает, в другой работает. Ставится двумя независимыми путями: сам себе — `PATCH /api/users/me/vacation` (тумблер в «Настройки → Аккаунт», роли не требует, компания берётся из токена), либо создателем компании/супер-админом в карточке сотрудника. Поле одно, поэтому пути не конфликтуют. tasksvc отдаёт 403 `ON_VACATION` на создание/правку/закрытие задач, смену ответственного/этапа и старт юнита (остановка активного разрешена; системные пути YouGile-вебхука не затронуты). petsvc: грувик «в отпуске вместе с хозяином» — `Pet.FreezeClocks` на read-пути сдвигает `needs_at`/`sick_since` вперёд (шкалы не тают, болезни не наступают, побег на паузе), начисления молчат, уход/приключения/поглаживания — 422 `PET_ON_VACATION`.

## WebSocket и presence

Realtime — gatewaysvc; фронт подключается тонкой обёрткой `front/src/socket/gateway.js` (socket.io-подобный API on/emit/connected/disconnect; реконнект 1с→5с; emit при обрыве буферизуется). Протокол — JSON-кадры `{"event", "data"}`: первый кадр клиента `{"event":"auth","data":{"token":<PASETO>}}` (10 с таймаут), сервер отвечает `_connected` (диспатчится как `connect`) или `_error` + close; пинг/понг 25с/60с. Комнаты `all` и `user_{id}`. Мутации приходят из сервисов через `gw2:<svc>:events` (envelope `{event, rooms, payload}`) и доставляются вербатим; company-scoped события несут `company_id` — клиент фильтрует в сторе. Presence — Redis (`gw2:presence:beats` ZSET + `gw2:presence:online` SET, мульти-инстанс-ready): онлайн = есть живая видимая вкладка (visibility + heartbeat 25с + sweeper 15с, простой >60с — офлайн), `last_seen_at` пишется в users на переходе в офлайн.

## Звонки (callsvc + LiveKit)

- Медиа-транспорт — LiveKit (сигнальный WS через nginx `/livekit`, медиа 7881/tcp + 7882/udp). NAT/VPN пробивает **встроенный в LiveKit TURN-relay** (только прод-оверлей: TLS 5349 + UDP 3478, cert — общий Let's Encrypt-том nginx, домен `LIVEKIT_TURN_DOMAIN`); LiveKit сам анонсирует TURN с эфемерными кредами — правок в callsvc/фронте не требуется. Внешний coturn не используем.
- **gRPC-контракт** `calls.v1.CallService`: StartCall / InviteToCall / AcceptCall / DeclineCall / LeaveCall / EndCall. Транспорт всегда OK; бизнес-ошибка — поле `error {code, message, http_status}`. Ответы несут готовый снапшот `Call` и списки адресатов — gateway эмитит события не читая БД.
- **gateway — тонкий шлюз ринг-фазы:** WS-команды `call:*` → `internal/ring` → gRPC callsvc; недоступность → `call:error {code:'CALLS_UNAVAILABLE'}`.
- Ринг-state — in-memory в callsvc (`internal/ringstate`), восстанавливается из БД+LiveKit. Лимит 9 участников (гости считаются). Identity: `u{user_id}`, гости `g-{hex}`.
- **Ссылки-приглашения:** `/call/<share_code>` — публичный роут; `GET/POST /api/calls/join/<code>` (гость представляется именем, авторизованный входит под собой).
- **Фронт:** `services/livekit.js` (`CallRoomManager`), `stores/call.js` (фазы idle/incoming/outgoing/active, чат звонка — data-канал topic `chat`, outgoing-таймаут 45 с, guard `handleEnded` по `call_id`), `CallView.vue` (mini-режим, демонстрация экрана, панели участников/чата), `CallAudioSink.vue`.
- **Инвариант: одно подключение на identity** — дубль рвёт звонок (`DUPLICATE_IDENTITY`); single-flight на rejoin и гарды подключения не ломать.

## Мессенджер

Домен в msgsvc. Диалоги 1:1 (`conversations`, уникальная пара, `company_id` НУЛЛАБЛЕ — переписка между людьми без общей компании разрешена), dev-чат поддержки (адресаты — супер-админы) и **групповые чаты**. Сообщения: текст (Markdown-подсветка по выделению), вложения до 500 МБ, ответы, пересылка (файлы копируются физически), закрепление сообщений (общее) и чатов (личное), soft-delete «у себя/у всех» (обе стороны скрыли → физическое удаление + чистка файлов), запись экрана, прикрепление задач (`kind='task'`) и постов портала (`kind='post'` с ЗАМОРОЖЕННЫМ превью, не живой JOIN). **Задача и пост — сущности компании**, поэтому уходят только тем, кто в ЕЁ компании состоит: `ensureCompanyAudience` сверяет всю аудиторию через `user_companies`, иначе 403 `TASK_WRONG_COMPANY`/`POST_WRONG_COMPANY`. Компания диалога тут не показатель — в кросс-компанийной переписке она вводит в заблуждение; выбор получателя на фронте сужен тем же правилом (`useContactPicker({ companyOnly: true })`).

**Реакции** (`message_reactions`): toggle, максимум `domain.MaxReactionsPerUser`=2 разных эмодзи от пользователя на сообщение (422 `REACTION_LIMIT`); событие — `message:updated` с полным снапшотом, реакции грузятся батчем (как вложения), группирует их клиент. **Пользовательский статус** (эмодзи+текст ≤80 в `users`) ставится в мессенджере, показывается в списке чатов, шапке диалога и профиле сотрудника (real-time рассылки нет — подтягивается при загрузке списков).

**Групповые чаты**: `conversations.is_group` (`company_id` NULL — cross-company) + `conversation_members` (роль owner|admin|member, `last_read_message_id`, `pinned_at`, `hidden_at`, `muted`, права can_manage_members/can_edit_info/can_pin_messages). Прочтения в группах — WATERMARK участника, не колонка `read_at`: непрочитанные = `id > last_read`, «кто прочитал» = участники с `last_read >= msg.id`. Веер сообщений — по всем участникам, пуш — только не-muted (`message:new` несёт `notify_ids`; системные плашки `kind='system'` пуш не порождают). Управление — `internal/service/groups.go`: создание, карточка/переименование (`can_edit_info`), аватар (через уже загруженное вложение), состав (`can_manage_members`), роли и передача владения (только owner), выход (владелец → владение самому раннему по `joined_at`; последний → группа удаляется), mute, ссылка-приглашение (`/group/:code`). Системные события — сообщения `kind='system'`; смена состава/ролей — событие `group:updated`. @упоминания обходят mute. Удаление сообщения в группе — всегда «для всех» (автор или owner/admin).

Инварианты UI:
- Прочтение: открытый+сфокусированный чат отмечает read сразу; плюс на возврат фокуса вкладки и при отправке.
- Меню действий сообщения: десктоп — ПКМ, тач — обычный ТАП по пузырю (long-press намеренно отдан браузеру под выделение текста). Свайп вправо — ответ. Кнопка «вниз» позиционируется над полем ввода динамически (ResizeObserver).
- Поле ввода: на десктопе Enter отправляет, Shift+Enter — перенос; на тач-устройствах Enter — перенос, отправка только кнопкой. Текст очищается только при УСПЕШНОЙ отправке.
- Плавающего хаба (FAB мессенджера/ассистента) НЕТ: переписка живёт в окне «Мессенджер», ИИ — во вкладке «Чат» Hola. Единственный плавающий виджет — питомец.
- Уведомления: Web Notifications через Service Worker + Web Audio «бип»; разрешение и разогрев AudioContext — по первому жесту. **Service worker существует ТОЛЬКО ради них** (на Android Chrome конструктор `new Notification()` запрещён, показать уведомление можно лишь через `registration.showNotification`): кэша и офлайн-оболочки в `public/sw.js` НЕТ и заводить их нельзя — кэшируя модули Vite, он ронял разделы на dev-сервере. Регистрация одна, в `utils/systemNotify.js`, и только в прод-сборке; офлайн-старт клиентов держат сами обёртки (сплэш с автоповтором в Electron, `error.html` в Capacitor).

## Питомцы-грувики

Чистая гейм-механика без ИИ, без публичной ленты и соцсети; все таблицы company-scoped, гейт компании — `GrooveEnabled`/`uses_groove` (в БД имя не переименовано — техдолг; пользователю показывается как «Питомцы»). **Плавающий компаньон, а не страница**: `FloatingPet.vue` монтируется глобально (draggable, снап к краю, speech bubble только на переходах состояния), тап открывает `PetDetailModal.vue`. Страница `/pets` — хаб для магазина, питомцев коллег и рейтинга.

**Экономика:** XP (эволюция по `domain.StageXP`; `applyEvolution` пересчитывает характер и ПРИРОДНЫЙ вид — купленный облик эволюция не сбрасывает) и валюта **кудосы** — начисляются НАПРЯМУЮ за работу с дневными капами по источнику в Redis (fail-open): юнит, закрытая задача. Хуки от tasksvc — единственный входящий gRPC. **Read-эндпоинты не пишут в БД впустую** (`GetMyPet`/`BumpQuest` сохраняют, только если что-то реально изменилось) — иначе частый поллинг рискует lost-update перезаписать конкурентное начисление хука устаревшим снимком.

**Потребности** (`domain/needs.go` ≡ `NEEDS`/`AILMENTS` в `front/src/utils/pets.js`): четыре шкалы 0..100 (сытость/энергия/чистота/общение), тающие со временем. Пересчёт ЛЕНИВЫЙ по `needs_at` (`ApplyNeedsDecay` на read-пути и в фоновом цикле): убывание задано целыми единицами за тик `NeedTick`=30 мин, `needs_at` сдвигается ровно на применённые тики — дробный хвост не сгорает при частом поллинге. **Настроение** — среднее шкал, где худшая весит втрое; `MoodFactor` (0.7…1.5) множит прямой XP за работу. Сохранение — узкий `SaveNeeds` (read-путь) и атомарный `AdjustNeeds` с RETURNING (хуки кладут результат в снапшот, а не досчитывают дельту — иначе конкурентный сдвиг учтётся дважды).

**Болезни** (`pets.ailment`, инвариант `ailment IS NOT NULL ⟺ sick_since IS NOT NULL`): у каждой своя причина и свой рецепт (`CureFor`, общий счётчик `RecoveryTarget`=3): `blues` — простой в РАБОЧИХ днях компании, `hunger`/`cold`/`grime` — пустая соответствующая шкала. Неверный рецепт даёт 0 очков — питомец подсказывает нужный. **Выздоровление поднимает шкалу-виновника до `RecoveredNeedFloor`** и чистит `ailment` — иначе вылеченный с нулевой шкалой заболевал бы снова в ближайший пересчёт. **Побег** (`RunawaySickDays`=14): атомарный `RunAway` с гейтом давности в WHERE (ленивый GET и фоновый цикл фиксируют побег ровно один раз) обнуляет ПРОГРЕСС (стадия/XP/вид/характер/стрик/потребности), кудосы, гардероб, домик, банк и поколения остаются; за 4 дня DTO несёт `runaway_in_days`.

**Уход:** платные действия с мини-играми (кормление, прогулка, аптечка — работает при ЛЮБОЙ болезни, купание) и БЕСПЛАТНЫЙ сон (энергия не должна упираться в кошелёк). Остатки лимитов приходят в DTO — кнопка гаснет до отказа, а не после. **Поглаживание чужого питомца** (`pet_strokes`, 3/день на пару): гладящий платит и получает 1 XP, а **ВЛАДЕЛЕЦ поглаженного — кудосы, XP и закрытую потребность в общении**, причём кудосы идут в недельный рейтинг и сезонный трек (поглаживание = признание). Общение — единственная шкала, которую хозяин сам не закроет. **Удаление питомца сотрудника** — администратор компании (`DELETE /api/pets/zoo/:user_id`, транзакцией чистятся связанные таблицы); свой питомец пересоздаётся первым `GetMyPet`.

**Магазин** (`pet_shop_items`/`pet_shop_purchases` — ассортимент правится данными, без деплоя) — 4 механики нестатичности: постоянные + ротационные товары (`active_from/active_to`), редкость, ограниченный тираж на компанию, достижения (не продаются) — плюс бесплатный ежедневный «сюрприз» (не лутбокс). **Скидка дня**: детерминированно от даты МСК + ключа товара часть витрины уценивается на 30/50% до полуночи (одна формула `salePrice` в витрине и в покупке).

**Развитие после максимальной формы:** **престиж** (поколение+1, стадия/XP в ноль, вид снова яйцо; кудосы/гардероб/домик сохраняются; атомарный UPDATE с гейтами в WHERE; поколения ≥2 разблокируют эксклюзивные виды), **сезонный трек** (кудосы за календарный квартал МСК открывают пороги; «награда один раз» гарантирует PK `pet_season_claims`), **домик** — кудос-сток: каталог декора, покупка атомарным UPDATE, СВОБОДНАЯ расстановка drag'n'drop (`house_placed` jsonb в % сцены), перемещение самого грувика, тема комнаты (визуал целиком на фронте, только токены); домики видны коллегам и служат сценой мини-игры поглаживания.

**Кудо-банк** (REST `/api/pets/bank/*`): **выписка** `pet_kudos_ledger` (каждое движение кудосов; журнальные записи fire-and-forget, банковские — транзакционно). **Переводы коллегам** — атомарная транзакция (guard по балансу + обе записи выписки), скоуп компании, событие `kudos:received` адресно (+FCM офлайн); рейтинг признания переводы НЕ двигают — для щедрости отдельный топ. **Вклад** (простой процент за целые сутки, лениво при обращении, кап) и **кредит** (один активный, вклад при долге закрыт — анти-арбитраж). **Уровни клиента** по `LifetimeEarned` (сумма заработанного без transfer_in/loan_taken/withdraw): выше ставка вклада, ниже комиссия, больше лимиты. **Копилки-цели** (лимит 4, движения кошелёк↔копилка одной транзакцией, `achieved_at` ставится однажды). **Благотворительные сборы** (объявляет менеджер, донат — транзакция с guard'ами; достижение цели переводит сбор в done в том же UPDATE; взносы не возвращаются). Статистика по дням МСК. Поля банка, престижа и домика в full-row `SavePet` намеренно НЕ входят — только узкие атомарные методы.

**Приключения** (appointment-механика): бесплатно отправить здорового питомца на 2–4 часа (кап 3/день); в пути платные действия и поглаживания дают 422 `PET_AWAY`; возврат фиксируется ЛЕНИВО первым `GetMyPet` после срока (атомарный UPDATE с RETURNING — награда ровно один раз), досрочный возврат — за 100 кудосов без награды.

**Прочее:** единый рендер эмодзи грувиков забандленными Twemoji SVG (`components/common/EmojiGlyph.vue` — одинаково на всех платформах; новый эмодзи в каталоге = докачать SVG). Рейтинг — кудосы с начала ISO-недели (`pet_kudos_weekly`). Приватная история (`pet_activity_log`) видна ТОЛЬКО владельцу. Убрано полностью: публичная лента, рейд недели, wrapped, AI-чат питомца, погода. События → `gw2:pets:events`.

Единая точка «спросить и найти»: поиск по приложению и в интернете, быстрые команды и чат с ИИ (заменил Spotlight и плавающий хаб).

- **Оболочек две, содержимое одно** (`components/hola/HolaPanel.vue`): на рабочем столе — всплывающая панель `HolaPopup.vue` (не окно раздела: ни кнопки в панели задач, ни адреса), на телефоне — тот же `HolaPopup` во весь экран между панелями каркаса. Открывают кнопка с фирменным значком и `Ctrl/Cmd+K`; deep-link `/hola` на десктопе разворачивается в ту же панель, адрес возвращается на пустой стол.

Переход идёт окном или сменой экрана — решает `shellActive` (одна точка `openPath`, разделы про Hola ничего не знают).
- **Интернет** — отдельной секцией: выдачу НЕ проксируем, строка ведёт на страницу поисковика в новой вкладке (`utils/webSearch.js` — встроить нельзя, поисковики запрещают фрейминг). Поисковик по умолчанию выбирается в «Настройки → Общие». **Введённый адрес сайта открывается напрямую**: `parseUrl` узнаёт «vk.com», «дом.рф», «github.com/user/repo?tab=1» — строка «Открыть …» встаёт первой. Домен проверяется по ИСХОДНОЙ строке, а не по `url.hostname` (там кириллица уже свёрнута в punycode); частые расширения файлов доменом не считаются.
- **История запросов** (`utils/holaHistory.js`, 12 последних) пишется на ВЫПОЛНЕНИИ перехода, а не на каждый символ.
- **Команды**: фразы разбирает `utils/quickCommands.js`, сроки и повторы — `utils/naturalDate.js`. Что создаётся молча, а что формой, решает наличие обязательных полей: заметка и доска создаются сразу, задача открывает форму, напоминание создаётся при распознанном сроке. **Отправка сообщения** («напиши Васе созвон в 15:00»): адресат опознаётся по основе имени (`utils/recipients.js`), выбор строки ОТПРАВЛЯЕТ сообщение и открывает чат.
- **Калькулятор строки**: `utils/calc.js` считает выражение во время ввода — свой разбор рекурсивным спуском, не `eval`.
- **Чат** (`HolaChat.vue`) — деловой ИИ-ассистент aisvc. **Недоступен без ЛИЧНОГО ключа**: настройки тянутся разово при открытии, вкладка объясняет, чего не хватает, и ведёт в `/settings?section=ai`. Активная компания не нужна — без неё лишь не работают инструменты статистики.

**Калькулятор-приложение** (`views/CalculatorView.vue`, окно `/calculator`) — обычный и инженерный режимы, градусы/радианы, память, история. Считает тем же движком: `evaluate()` из `utils/calc.js` (в отличие от `calculate()`, ему не нужен знак действия — в калькуляторе пользователь заведомо считает). Табло — редактируемое поле. Раскладка тянется за размером ОКНА (`container-type: size` + `cqmin` с px-фолбэком для старых WebView).

## ИИ-ассистент

Расширение aisvc, не отдельный сервис. **Подключён к КОНКРЕТНОМУ ПОЛЬЗОВАТЕЛЮ, а не к компании**: ключ в `user_ai_settings`, заводит его себе каждый сам (`GET/PATCH /api/ai/my-settings`, `POST …/test`; сырого ключа сервер не отдаёт, только маску). Ключ переезжает за человеком между компаниями и работает без активной компании — тогда недоступны только инструменты компанийной статистики (tools не предлагаются вовсе, и системный промпт честно предупреждает модель). Клиент на личном ключе — свой кэш, правка настроек инвалидирует его сразу; эмбеддинги задач/заметок и ТВ-факт остаются на ПЛАТФОРМЕННОМ ключе.

Никакой «сладкой» тональности и привязки к питомцу — единый `assistantSystemPrompt` требует опираться ТОЛЬКО на факты из инструментов, не выдумывать цифры и присылать прямую ссылку на найденную задачу. **Tools-цикл внутри aisvc** (`chatWithTools`, до 4 итераций поверх одноходового `Chat` — внутрипроцессно, не gRPC-петля на себя): 5 статистических инструментов через gRPC tasksvc (период `today/yesterday/this_week/last_week/this_month/last_month/7d/30d`) и `find_task` (SemanticSearch → GetTaskLink → ссылка `APP_PUBLIC_BASE_URL/tasks/{id}`). Диалог — одна запись на ПОЛЬЗОВАТЕЛЯ (`ai_assistant_conversations`, UNIQUE user_id); переключение компании историю не подменяет. **Провенанс**: строка «Данные: …» из реально вызванных инструментов сохраняется и показывается под ответом. **Обратная связь** 👍/👎 (+причина) — `ai_assistant_feedback` (upsert), свой голос приходит в history.

**ИИ-инструменты текста заметок** — `internal/service/texttools.go`, `POST /api/ai/text-tools {action, style?, text}` → `{text}`: одна операция одним ходом Chat (без tools-цикла и сохранения диалога); actions improve/fix/rephrase/shorten/expand/simplify/summarize/bullets/continue + tone + translate. Ссылки на задачи в ответах — обычный текст, автолинкифицируется `utils/linkify.js`.

## Экраны входа и адреса приложения

**Корень `/` — промо-лендинг** (`PromoView`, публичный, `meta.fullscreen` + `meta.authScreen`; `/promo` — редирект на него): герой, три опоры, сетка возможностей, чередующиеся секции, короткий блок про грувиков, устройства со СКАЧИВАНИЕМ клиентов (общий `useAppDownloads` — имена артефактов и номер сборки из `/apps/*/version.json`), FAQ на `<details>`. Рассказывает про РАБОТУ, геймификация — одним абзацем; рисуется классической темой на общих токенах.

Само приложение начинается с **`/home`** — «пустой стол» (`HomeView`, на мобиле уводит в стартовый экран), туда же ведут выход из шагов входа и незнакомые адреса. Обёртки (десктоп/Android) открывают прод-адрес СРАЗУ с `/home` — на корне их встретил бы лендинг; гард `inAppShell()` разворачивает корень на `/home` (страховка для установленных ранее сборок).

**Экраны входа помечены `meta.authScreen`** и оформлены единым языком «волны»: `/welcome`, `/login`, `/register`, `/qr-login`, `/tv-activate`, `/verify-email`, `/forgot-password`, `/reset-password`. Вошедшему формы входа недоступны (гард уводит в стартовый раздел); остальные открыты и с живой сессией — на них приходят по ссылке из письма.

- **Оформление — классическая тема в системном светлом/тёмном виде**, личная тема на экраны входа НЕ протекает (за устройством может быть гость): гард зовёт `theme.setAuthPreview`, стор подменяет палитру на `classic` и берёт тёмный режим у ОС. Плитки и подписи оформления показывают `theme.activePreset` — тему, которая ФАКТИЧЕСКИ на экране, а не личную из `localStorage`. Исключение — оформление, выбранное прямо на регистрации, но и оно ЧЕРНОВИК: `startThemeTrial/commitThemeTrial/cancelThemeTrial` держат цвет и светлый/тёмный вид вне `localStorage`, закрепляет их только созданный аккаунт, а уход с регистрации любым способом откатывает (иначе выбор гостя оставался бы на устройстве хозяина).
- **Каркас** — `components/auth/AuthShell.vue`: фон-волна, стеклянная карточка с маркой, заголовок СТРОЧНЫМИ, подвал; ширины `sm`/`md`/`lg`, слоты `hero`/`actions`/`overlays`.
- **Фон** — `AuthWave.vue`: ТРИ волны, каждая — самостоятельное матовое стекло; форма задана CSS-маской-синусоидой в один период, сдвиг ровно на период даёт бесшовный ход. `prefers-reduced-motion` останавливает движение, `@supports not (backdrop-filter)` заменяет стекло заливкой.
- **Общие детали форм** — `AuthField.vue` (метка + поле + слот `tools`) и `AuthThemeTiles.vue` (цвет плитками + светлая/тёмная).
- **Вход — три шага в одной карточке** (`LoginView`): учётные данные → выбор компании → обязательная смена пароля. Вход по QR и активация ТВ-киоска — самостоятельные экраны поверх общего `DeviceLinkInitiator`.
- **Регистрация** (`RegisterView`): фото профиля, поля в две колонки, выбор оформления (цвет плитками + светлая/тёмная). Аватарку до подтверждения почты загрузить некуда (сессии ещё нет), поэтому обрезанный снимок ждёт в `localStorage` (`utils/pendingAvatar.js`) и уходит на сервер сразу после `verify-email`.
- В том же языке — смежные публичные страницы: возврат из Яндекс ID (в т.ч. по deep link), подтверждение спаривания устройства, согласие OAuth Алисы, приём приглашений в компанию и группу.

## Рабочий стол (десктопный каркас)

Каркас ОДИН по смыслу и два по раскладке: широкий экран (>768px, авторизован, не fullscreen-роут) — **рабочий стол** `components/desktop/DesktopShell.vue`, телефон — **мобильный каркас** (см. ниже). Прежней навигации «сайдбар + нижняя панель» нет вовсе.

Общее вынесено в `desktop/shellCore.js` (`useShellCore`): права на раздел, обои, сводки живых плиток, синхронизация адресной строки, чистка при выходе. Каркас передаёт `activePath()`, толщину и отступ своей панели задач (`barHeight`/`barMargin`), предел открытых разделов и способ записи адреса (`replace` на столе, `push` на телефоне) и зовёт `boot()` из своего `onMounted` — ПОСЛЕ расчёта геометрии.

- **Окна.** Раздел открывается окном; одному разделу можно открыть несколько (Ctrl/Shift/средний клик, «+» на плитке, ПКМ по кнопке панели задач). Окно тянется за заголовок, липнет к краям и углам, разворачивается, сворачивается; **развёрнутое окно — полноэкранный режим** (геометрия из `screen`, а не из рабочей области; панель задач уезжает вниз и выезжает по подведению указателя). Свёрнутое окно остаётся смонтированным (`v-show`) — состояние не теряется. Перекрытие задаёт z-index, порядок массива не меняется (иначе перефокусировка перемонтировала бы разделы).
- **Модалки раздела живут в СВОЁМ окне.** Хост телепорта раздаёт окно (`desktop/windowHost.js`: `provideWindowHost` в `AppWindow`, `useModalHost()` у модалок) — цель `<Teleport>` и `appendTo` PrimeVue становится тело окна. Позиционирование тянется само: у окна есть `transform`, поэтому оно служит containing block для `position: fixed` потомков. Руками задаются две вещи (общее правило `.gw-in-window-mask` в `main.css`): маске — `position: absolute !important` (инлайновый `fixed` от PrimeVue меряет экран; absolute отмеряется от `.win-body`, поэтому заголовок окна остаётся живым) и клампы габаритов (их считают в `vw/dvh`, а экран больше окна). Вне рабочего стола инжекта нет — цель прежняя `body`, поэтому один компонент годится и разделу в окне, и глобальному виджету. Меню и попапы у курсора (`ContextMenu`, `EmojiPicker`, `ReactionPicker`, …) НАМЕРЕННО остаются в `body`: они позиционируются экранными координатами клика. **Раздел при этом лежит в СВОЁМ контейнере `.win-view`, а не прямо в теле окна** (то же и на телефоне: `.mscreen-body` внутри `.mscreen`): `Teleport` оставляет в цели пару пустых текстовых узлов даже у закрытой модалки, а Vue берёт якорь вставки ДО демонтажа старого раздела и перешагивает ровно один телепорт — с двумя закрытыми диалогами вставка падала с `NotFoundError` и роняла окно целиком.
- **Стор** `stores/desktop.js` — окна, геометрия, z-порядок, свёрнутость, история переходов окна, рабочая область (`area`) и полный экран (`screen`), сессия в `gw_desktop_session` (восстанавливается при загрузке, разделы без прав отбрасываются). Чистая геометрия — `desktop/geometry.js`.
- **Содержимое окна** (`WindowContent.vue`) грузит компонент ленивым чанком с ПОВТОРОМ и видимой ошибкой: не доехавший чанк (моргнула сеть, после выката поменялись имена файлов) раньше оставлял окно пустым.
- **Реестр** `desktop/apps.js` — только «оконные» свойства раздела (заголовок, иконка, группа «Пуска», стартовый и минимальный размер, правило доступности). Пути и компоненты остаются в `router/index.js`: окно берёт компонент из `router.resolve(path).matched`.
- **Маршрут окна** — `desktop/windowRoute.js`: окно провайдит СВОИ `routeLocationKey`/`routerKey`, поэтому разделы пользуются обычными `useRoute()/useRouter()` и про окна не знают. Переход внутри своего раздела идёт по истории окна, в чужой — открывает его окно, внешние экраны уходят настоящему роутеру.
- **Адресная строка отражает активное окно** (`router.replace` на смене фокуса; deep-link открывает нужное окно). Поэтому `/home` — полноценный маршрут, а не redirect. Полоса навигации показывается с задержкой 150 мс (`useNavProgress`).
- **Слои:** окна 10…800, панели каркаса 900, «Пуск»/центр уведомлений 950, панель Hola 960, диалоги PrimeVue ~1100 (намеренно перекрывают панель), модалка активного юнита 9999, плавающий питомец ~10055, тосты 11500. Размеры — `desktop/layout.js` (`--taskbar-height`, `--statusbar-height`, `taskbarMargin`, `taskbarReserve()`); питомец поднимается через `floatingBottomInset()`, `shellActive` говорит разделам, открывать окно или менять экран.
- **Панель задач**: край выбирает пользователь (`desktop_prefs.taskbarSide` — снизу/сверху/слева/справа; `desktop/layout.js` считает по стороне рабочую область, автоскрытие и отступ питомца). У вертикальных сторон панель — колонка значков. Горизонтальная: центрирована, ширина по содержимому до предела, дальше кнопки прокручиваются; зоны разделены тонкими разделителями — «Пуск», закреплённые и открытые разделы, справа чип активного юнита, часы и центр уведомлений. Свою геометрию панель публикует в стор (`taskbarRect`) — по её правому краю выравнивается центр уведомлений. Обе всплывающие панели рисует сам стол, а не панель задач: у панели `transform`, а он стал бы точкой отсчёта для `fixed` потомков. Закреплённый неоткрытый раздел — кнопка-ярлык; открылся — та же позиция стала кнопкой окна. Закреплённые переставляются перетаскиванием, незакреплённые — нет (их порядок задаёт очерёдность открытия).
- **Меню «Пуск»**: кнопка разворачивает его на весь экран (и настройка «всегда во весь экран»). По умолчанию — две стеклянные подложки: слева марка (общий `BrandWordmark`, ведёт в «О приложении») и разделы с плитками в сетке 4 колонки, плитка **широкая** (2 колонки) или **квадратная**; размер и закрепление — в контекстном меню, порядок и **перенос между разделами** — перетаскиванием. **Разделы редактируемые**: встроенные переименовываются, свои создаются/удаляются (плитки возвращаются в родные), любой сворачивается (`grid-template-rows: 1fr→0fr`). Внизу подвал одной строкой: аватар, пилюля активной компании, настройки, выход.
- **Живые плитки** (в духе Metro): плитка по очереди показывает «грани» — сводки своего раздела (`LiveTile.vue`, переворот раз в 5 с со стаггером; замирает под курсором, при `prefers-reduced-motion` показывает первую грань статично). Набор граней — чистая функция `desktop/liveTiles.js` (`tileFaces(appId, ctx)`). Источники: уже загруженные сторы + `stores/liveTiles.js` — лёгкие сводки ПАРАЛЛЕЛЬНО (`Promise.allSettled`, упавший источник гасит только свою грань), только для доступных разделов, TTL 60 с и склейка параллельных вызовов. Тянет их сам каркас заранее и по таймеру (в скрытой вкладке не опрашивает). Тумблер — «Настройки → Рабочий стол»; выключено — обычные значки и никаких запросов.
- **«Моя активность»** — правая колонка «Пуска» (`ActivityPanel.vue`), отданная ей целиком. Лента — ОДИН поток: открытые разделы (журнал пополняет `desktop.open()`; восстановление сессии идёт мимо него, поэтому перезагрузка список не перетасовывает) и созданное пользователем (задача, заметка, запись ежедневника/календаря/реестра, публикация). Клик открывает окно прямо на элементе. Журнал — `stores/activity.js` (localStorage, до 40 записей; повтор поднимает прежнюю строку), пишется через `utils/activityLog.js`, чистится на выходе. Это личная история сеанса, а не серверный аудит. Узкий экран (<860px) колонку скрывает.
- **Центр уведомлений** (`composables/useDesktopNotifications.js` — состояние модульное, одно на панель и на бейдж). Строки двух родов: **журнал** (`gw_notif_journal`, до 40, TTL 7 дней) — разовые события, которые больше нигде не хранятся (сработавшее напоминание, перевод кудосов, упоминание, побег грувика): кладёт `pushNotification()`, переживают перезагрузку, убираются крестиком насовсем; **живые** — производные от сторов (непрочитанные чаты, новые посты, болезнь питомца): «убрать» скрывает до следующего изменения (отпечаток-счётчик). Бейдж = число карточек (три сообщения в одной переписке — одна карточка). Журнал чистится при выходе.
- **Звук и «не беспокоить»**: звучит ЛЮБОЕ уведомление — `notify()` играет голос по severity (`utils/systemNotify.js`, синусоиды Web Audio; пачка сводится к одному звуку окном 250 мс); у события со своей мелодией — `notify({ sound: false })`. ПКМ по кнопке уведомлений — «Отключить» с подменю сроков либо «Включить»; состояние `gw_notify_muted`, обёртка `composables/useNotifyMute.js` (сама гасит тишину по истечении), тот же источник у тумблера в настройках. Тишина глушит ЗВУК и всплывашки ОС; карточки продолжают копиться, звонки не глушатся.
- **Полный экран браузера** — указатель у ВЕРХНЕЙ кромки выдвигает кнопку; это режим самого браузера (F11), а НЕ развёрнутое окно: работа с ним в `utils/pageFullscreen.js` (префиксы, подписка на `fullscreenchange` — режим меняют и клавишей). Без Fullscreen API кнопки нет.
- **Анимации**: «Пуск» и центр уведомлений выезжают из панели задач; окно при сворачивании улетает в панель задач (вектор `--fly-x/--fly-y` от центра окна к центру панели).
- **Личные настройки стола** (закреплённые разделы и порядок, разделы «Пуска» с составом/свёрнутостью, размеры плиток, живые плитки, обои и история 10 картинок) — `users.desktop_prefs` через `GET/PUT /api/users/me/desktop`; фронт — `stores/desktopPrefs.js` (localStorage только кэш первого кадра, сервер главнее, запись отложенная). Стол одинаков на всех устройствах пользователя.
- **Обои** — рецепт фона в тех же настройках; рисует общий `ChatBackgroundLayer.vue` (он же фон чатов и портала), редактор — общий `BackgroundEditor`. **Встроенный комплект** `utils/wallpapers.js`: пары «светлая/тёмная» из `front/public/bg` (WebP — PNG-исходники весили по 1–1,5 МБ против 20–70 КБ), в рецепте хранится КЛЮЧ (пути пересобираются на чтении, тёмную выбирает слой по `theme.dark`). **Пополнение комплекта — два файла и строка**: `front/public/bg/<ключ>-light.webp` + `<ключ>-dark.webp` (каталог `public` уезжает в сборку как есть и раздаётся nginx по `/bg/...`) плюс `wp('<ключ>', 'Название')` в `WALLPAPERS`. Помимо картинки рецепт умеет однотонную заливку (`solid`: роль токена + сила подмеса — цвет следует теме) и узор. Свои обои не выбраны → комплект по умолчанию; **снятые вручную слои означают пустой фон** — своей декоративной подложки у каркасов нет.
- Тура по интерфейсу нет: он вёл по сайдбару прежнего каркаса.

## Мобильный каркас

Телефон (≤768px) получает тот же каркас-«ОС» в раскладке Windows 10 Mobile: `components/mobile/MobileShell.vue` — обои, панель статусов сверху, стартовый экран, слой разделов и панель задач снизу. Разделы открываются ТЕМ ЖЕ стором, что и окна стола, поэтому переключение сохраняет состояние, а личные настройки плиток и закреплений общие с настольным каркасом.

**Обе панели прижаты к кромкам экрана** — без полей, скруглений и тени; системные вырезы они отбирают отступом, а не высотой содержимого. **Место разделу отводит `AppScreen`** (`inset` между панелями с учётом safe-area), поэтому сам раздел из потока НЕ вырывается: `position: fixed` и свои компенсации `env(safe-area-*)` в разделах — ошибка, она даёт заезд под панель статусов и двойные отступы. На телефоне раздел примыкает к панелям вплотную — `AppPage` там идёт без полей, а его панель теряет рамку и скругления. Толщины панелей каркас публикует переменными на КОРНЕ документа (`--taskbar-height`, `--statusbar-height`) — их читают и всплывашки, телепортированные в `body` (тосты).

- **Панель статусов** (`MobileStatusBar.vue`) видна ВСЕГДА, в том числе поверх открытого раздела: активная компания (общий `CompanySelect`), чип идущего юнита, центр уведомлений (долгое нажатие — «не беспокоить») и аватар (→ «Настройки → Аккаунт»).
- **Стартовый экран** (`MobileStart.vue`) — то же меню «Пуск»: марка «Groove Work N» над плитками (→ «О приложении») и плитки по разделам. Плитки — общий `LiveTile` (живые сводки, тумблер тот же), размер `wide`/`square` из настроек. Сетка адаптивная: `repeat(auto-fill, minmax(--mst-tile, 1fr))` — колонок столько, сколько влезает, и ряд делится поровну. Долгое нажатие (`composables/useLongPress.js`) открывает меню плитки, на пустом месте — «Персонализация» и «Выйти».
- **Панель задач** (`MobileTaskbar.vue`): слева «Пуск» (качели: со стартового экрана возвращает к последнему разделу), по центру лента закреплённых и открытых разделов (значок + точка у открытых; повторный тап по активному уводит на стартовый экран, долгое нажатие — закрыть/закрепить), справа кнопка Hola.
- **Всплывающие панели** (центр уведомлений, Hola) разворачиваются МЕЖДУ панелями каркаса и лежат слоем ниже них (890): иначе повторное нажатие кнопки попадало бы в подложку, а не в саму кнопку. Тосты выходят СВЕРХУ, под панелью статусов.
- **Экран запуска** (`AppSplash.vue`): при ПЕРВОМ открытии раздела поверх него на ~0,5 с показывается значок и название; возврат к открытому — мгновенный.
- **Навигация «назад»** отдана истории браузера: каркас пишет адрес через `push`, поэтому системная кнопка/жест ходят по разделам сами, а `/home` означает «стартовый экран». Перехвата `popstate` и жестов нет.
- **Предел открытых разделов** — 6: они остаются смонтированными, поэтому самый давний по последнему обращению закрывается сам.
- Модалки разделов телепортируются в `body` (хост окна — только у настольного каркаса): на экране всё равно один раздел.

## YouGile-интеграция

Целиком внутри tasksvc: инфраструктура — `internal/yougile` (HTTP-клиент REST v2 с ретраями 429/5xx, парсер ссылок, Fernet-крипто), бизнес-логика — `internal/service/yougile_*.go`, REST `/api/yougile/*` (формы ответов байт-в-байт с прежним Flask-блюпринтом). Per-company настройка (администратор подключает компанию/проект/доску; личных подключений у пользователя может быть НЕСКОЛЬКО — по одному на пространство YouGile, работает помеченное `is_active` (частичный уникальный индекс), переключение `POST /api/yougile/accounts/:id/activate`; ключи шифруются Fernet — `YOUGILE_ENC_KEY`, ротация ключа = потеря привязок). Импорт карточек по короткой ссылке (резолв перебором колонок + BFS по подзадачам), экспорт задач, отвязка, системные комментарии в обе стороны. Двусторонняя синхра: исходящий пуш — внутренний вызов после update/archive/restore (горутина, best-effort); входящая — публичный вебхук `POST /api/yougile/webhook/<companyId>/<secret>` (нужен `YOUGILE_WEBHOOK_PUBLIC_BASE`; constant-time проверка секрета, неверный — 404). Антицикл: `yougile_sync_hash` (sha1 от title|deadline_ms|completed) — вебхук игнорит собственное эхо. Инвариант: задача с активным юнитом не архивируется даже по completed из YG. Закрытие из вебхука зовёт petsvc OnTaskClosed.

## Оформление разделов и «Настройки»

**Всё собирается из ядра `front/src/components/ui/`** — других каркасов на платформе нет: `AppPage` (каркас раздела: название строкой, ниже строка управления `#subhead`, команды при названии, тело со своим скроллом), `AppListDetail` (раскладка «список ⇄ содержимое»), `AppCommandBar`, `AppRow`, `AppCard`, `AppTile`, `AppGrid`, `AppStack`, `AppButton`, `AppChip`, `AppTabs`, `AppSwitch(Row)`, `AppInfoBar`, `AppFab`, `AppDialog`, `ConfirmDialog`. Прежние `.gw-*`, `.admin-page`, `.hub-panel`, `.split-view` и компоненты `PillTabs`/`SegmentedTabs`/`SettingRow`/`SettingCard`/`SwitchRow` УДАЛЕНЫ — воскрешать их нельзя, свои стили заводить только на специфику раздела.

**Шапка раздела экономит высоту в тесной панели** (`narrowPage` < 640px по СВОЕЙ ширине): поиск раздела передаётся слотом `#search` (не `#subhead`) — там он сворачивается в лупу и встаёт В СТРОКУ НАЗВАНИЯ, а широкая панель ставит его в строку управления; переключатели, которым не хватает места (вид периода, набор записей, режим статистики), уезжают подменю в «ещё» — `AppCommandBar` понимает `children` у команды. Навигация по периоду у календарей и ежедневников — общий `components/common/PeriodNav.vue` (виды — `utils/periodViews.js`, там же готовая команда-подменю). Пустых строк шапка не рисует: строка управления появляется, только когда в ней ЕСТЬ что показать.

**Режимы `AppPage` под нестандартные экраны:** `embedded` — колонка внутри `AppListDetail`; `headless` — шапку рисует сам раздел (редактор заметки: статус сохранения, соавторы, масштаб, поиск); `bare` — без панели и фона (холст доски); `flush` — тело без полей (лента портала со своими обоями); `:scroll="false"` — прокручивается содержимое, а не тело. **При `scroll=false` содержимое ОБЯЗАНО скроллиться само** (`flex: 1; min-height: 0; overflow-y: auto`) — иначе список молча обрезается.

**Узкая раскладка считается от ширины ПАНЕЛИ, а не экрана** (раздел живёт окном, media-запросы про его размер ничего не знают): `AppListDetail` меряет себя ResizeObserver'ом и отдаёт слотам `narrow` — по нему решают, показывать ли кнопку «назад» и сворачивание панели. **Первичную загрузку раздела показывает `AppListDetail loading`**, а не `AppPage :loading` колонки-списка: в колонке лоадер оказывался в её узкой полосе у левого края, вместо центра раздела (передавать «списка ещё нет», иначе обновление списка гасит открытую запись). `isMobile` (ширина экрана) остаётся только для вещей про само устройство — мобильную клавиатуру, тач-жесты.

**Грабли `AppCard`:** он ставит содержимое в КОЛОНКУ и имеет `.card.no-gap { gap: 0 }` — оба перебивают внешний scoped-класс по специфичности. Строчная раскладка внутри карточки требует явного `flex-direction: row`, а промежуток надёжнее задавать пропом `:gap="N"` (он идёт inline-стилем).

**Строка настройки — `AppRow`** (`title` + `hint` + управление в слоте, `inline` для компактного). Раскладка считается от ширины СТРОКИ (`@container`, дубль `@media` для старого WebView): в узкой строке ШИРОКОЕ управление переезжает под текст и растягивается, компактное (переключатель, шеврон) остаётся справа, как в настройках мобильных ОС. Тумблер — `AppSwitchRow`. Свои `.xx-card`/`.xx-row` в разделах настроек не заводить.

**Декоративных иконок-плашек НЕТ**: значок в цветном квадрате слева от заголовка убран по всей платформе — остаётся только текст. Иконки остаются там, где они функциональны: кнопки и вкладки, навигация, панель задач и плитки, аватары, счётчики, шевроны и чужие фирменные знаки.

**Раскладка считается от ширины ОКНА, а не экрана**: разделы живут окнами, поэтому узкие состояния задаются `@container` (и дублируются `@media` для заводского WebView старых Android, который `@container` не знает) либо ResizeObserver'ом, когда от ширины зависит поведение.

**Горизонтальной прокрутки у раздела быть не должно.** Две типовые причины, обе про то, что колонка не умеет сжиматься: `1fr` — это `minmax(auto, 1fr)`, то есть не уже своего min-content (писать `minmax(0, 1fr)`), а `repeat(auto-fill, minmax(250px, 1fr))` в панели уже 250px оставляет колонку в 250px (писать `minmax(min(250px, 100%), 1fr)`). Сюда же — `flex: 1` без `min-width: 0` и пользовательский текст без `overflow-wrap: anywhere`: одно длинное слово в названии раздувает min-content всей сетки. Скрывать это `overflow-x: hidden` нельзя — прячет причину, а на тач-устройстве ещё и ломает жесты.

**Блочные лоадеры — только `BrandLoader`** (88/64/48/40); `ProgressSpinner` — лишь для инлайн ≤22px. **Только кастомные/общие компоненты**: никаких голых `input`/`button` — поля PrimeVue, кнопки ТОЛЬКО `AppButton` (`variant`: filled — главная, glass — вторичная, text, icon; `tone` — primary/danger/success/neutral), действия модалок через `AppDialog actions`. Глобальных `.btn-grad`/`.btn-glass` больше нет.

**Настройки** (`views/SettingsView.vue`) — две панели: список разделов с поиском и сам раздел; узкая шелла (<720px по СВОЕЙ ширине, меряет ResizeObserver) превращает их в один экран с «назад». Каталог — `utils/settingsSections.js` (его же ищет Hola; `resolveSectionKey` держит старые ссылки). Раздел с полем **`to` — не панель, а ССЫЛКА** на самостоятельный раздел; такой один — **Компании** (`/companies`): клик уводит сразу по адресу, в списке он помечен стрелкой «наружу». Панели: **Общие** (поисковик Hola, личный YouGile), **Темы и оформление** (карточка режима светлая/тёмная/системная/по времени + расписание, аккордеоны встроенных/загруженных/своих тем компактными карточками `ThemeCard`, `ThemeEditorDialog` с живым превью и откатом при закрытии, импорт-экспорт JSON), **Рабочий стол** (обои, градиент фона, живые плитки, десктоп-клиент), **Чаты и портал** (фон переписки и ленты), **Аккаунт**, **Хранилище** (сколько места занято и чем именно: разбивка по разделам, самые крупные файлы с удалением, сверка с владельцами при открытии), **ИИ возможности** (общий тумблер, отдельные тумблеры функций, выбор модели, остаток токенов с кнопкой в магазин, свой ключ свёрнутым блоком), **Справка и поддержка**, **О приложении** (версия/сборка/дата, «Что нового», скачивание и обновление обёрток) и — группой «Система» супер-админу — **Аудит платформы** (вкладки «Тарифы и цены», «Подписки», «Промокоды», «Товары», «Заказы», «ИИ возможности», «Данные», «Журнал») и **Резервная копия**.

## Цветовая система фронтенда

`front/src/assets/tokens.css` — Material You Expressive / M3, слои:
1. `--ref-*-h/c/l` — параметры цвета (пишет `theme.js`)
2. `--_p-*`, `--_s-*`, `--_n-*` — тональные палитры OKLCH
3. `--color-*` — семантические токены (primary, surface, error, success…)

`[data-dark="true"]` — тёмная тема. Режим: light | dark | **system** (следует за `prefers-color-scheme`) — `stores/theme.js`, localStorage `gw_theme_mode`. Для старых iOS без oklch — hex-фолбэк через `@supports not (color: oklch(0 0 0))` в конце tokens.css.

**Градиент фона приложения** (концепция «Expressive Glass», `front/DESIGN.md`): фон `.app-layout` — 4 радиальных пятна из цветов темы, включён по умолчанию. theme.js хранит рецепт (роль токена/позиция/размер/доля) и пишет слои в `--bgg-1..4`; цвета — `color-mix` от `var(--color-*)`, т.е. градиент сам следует за темой. Всё стекло (`--acrylic-*`) держится на этом просвечивающем градиенте: `--acrylic-card-bg` = плотность `--acrylic-bg`, но без blur (blur — плавающим слоям и крупным панелям-каркасам).

**Цвета-теги задач:** 8 пастельных цветов, токены `--tag-<name>-surface/-border/-accent`; набор продублирован в `front/src/utils/taskColors.js` и `domain.TaskColors`.

**Фирменные знаки чужих сервисов** — `YandexLogo.vue` и `YougileLogo.vue` (inline-SVG, prop `size`): цвета бренда заданы значениями намеренно — чужая айдентика не следует нашей теме (то же исключение, что и у шаблонов писем); подложку-кружок под таким знаком не рисуем.

**Правила:** никаких `#hex`/`rgba()` в компонентах — только токены (исключения перечислены выше). У круглых кнопок ВСЕГДА задавать min/max width И height равными размеру: глобальный мобильный `button { min-height: 36px }` иначе растянет их в овал. `-webkit-backdrop-filter` писать ПЕРЕД стандартным `backdrop-filter` (минификатор иначе выкидывает стандартное свойство); родитель с `backdrop-filter` — backdrop root, вложенное стекло уже ничего не размывает.

## Вес бандла

**Инициальная загрузка (entry + `modulepreload`) — только каркас** (Vue, router, pinia, сторы, стол/телефон, Toast). Это цена ЛЮБОГО захода, включая лендинг и экран входа, поэтому в неё не должны попадать: UI звонка и `livekit-client`, всплывающие панели каркаса («Пуск», уведомления, Hola), панели «Настроек», PrimeVue Dialog/DataTable/Select, Twemoji. Ориентир — **~610 КБ / 177 КБ gzip**; выросло вдвое — что-то статически импортировали из App.vue или каркаса, проверять по `modulepreload` в `dist/index.html`, а состав чанка — по sourcemap-сборке (`vite build --sourcemap` во временный `outDir`).

- **Приём для глобальных оверлеев:** `v-if` по состоянию + `defineAsyncComponent`. Одного `defineAsyncComponent` НЕ хватает — компонент без `v-if` монтируется сразу и тянет свой чанк на старте. Если внутри такого компонента есть `<Transition>` вокруг корня, ему нужен `appear`: раньше монтирование происходило заранее и анимировался только `v-if`, теперь монтирование совпадает с показом.
- **Вендоров руками НЕ дробим** (`manualChunks`): порядок загрузки чувствителен для заводского WebView старых Android (см. `build.target`). Режем только по границам динамических импортов — этого достаточно.
- **`livekit-client` грузится лениво** внутри `services/livekit.js` (`loadLivekit()`, single-flight): стор звонков нужен App.vue всегда, поэтому статический импорт клал полмегабайта в первый кадр. Синхронные `mediaState/getTrack` берут `Track` из загруженного модуля — они работают только при живой комнате, то есть заведомо после загрузки.
- **Twemoji не инлайнятся** — `build.assetsInlineLimit` в `vite.config.js` возвращает `false` для `/twemoji/`: `utils/emoji.js` берёт весь каталог `import.meta.glob`, и при инлайне 80 глифов давали чанк на 130 КБ там, где нужен один. Теперь это обычные файлы с хешем — качается только показанный.
- **Версия выпуска кэшируется** (`useAppVersion`, `gw_release` в localStorage, TTL 6 ч): марка «Groove Work N» стоит на каждом экране входа и в «Пуске», и без кэша `/api/changelog` уходил на каждом заходе ради одной цифры. «О приложении» читает через `load({ force: true })` — там смотрят актуальный выпуск.
- **Известные тяжёлые ленивые чанки** (грузятся по требованию, это нормально): `livekit-client` 513/133 КБ gzip, редактор заметок 439/138, PrimeVue DataTable 259/54 (статистика, пользователи), jsQR 132/49. В чанке редактора сидят `tippy.js` + `@popperjs` (~139 КБ исходника) — они приходят транзитивно с `@tiptap/vue-3` (зависимости `extension-bubble-menu`/`floating-menu`) и НЕ вытряхиваются tree-shaking'ом, хотя мы их не используем; уйдут только с обновлением TipTap. Подменять `tippy.js` алиасом-заглушкой нельзя — это мина для того, кто однажды добавит BubbleMenu.

## Локальная разработка

```bash
./dev.sh             # одна команда: инфра в Docker (+ mailpit) + миграции + Go-сервисы + Vite :5173
# или по частям:
make dev-infra       # DB + Redis + LiveKit (:7880)
make dev-migrate     # goose-миграции
make dev-<svc>       # calls|auth|messenger|ai|pets|tasks|gateway|push|mail|registry|calendar|
                     # diary|portal|notes|board|reminder|billing|alice — go run сервиса
make dev-front       # Vite :5173
make dev-stop        # остановить dev-контейнеры
make dev-stack       # ВЕСЬ стек в Docker (прод-подобно, фронт :8080)
make gen-proto       # перегенерировать gRPC-стабы после правки *.proto (выборочно: scripts/gen_proto.sh pets)
```

- **Compose (deploy/):** база `docker-compose.yml` (все сервисы + healthchecks, цепочка depends_on: db/redis → migrate (run-once) → сервисы → tasks → alice → nginx) + dev-оверлей `override` (порты инфры наружу; приложения за `profiles: [full]` — голый `up` поднимает только инфраструктуру) + прод-оверлей `prod` (только парой `-f ... -f ...`: обязательные секреты, TLS/certbot, nginx.prod.conf).
- **Миграции:** goose, `back-go/migrate/migrations` (00001 — baseline всей схемы). Существующая БД с `alembic_version` усыновляется автоматически. Новые изменения схемы — обычные goose-файлы `0000N_*.sql`.
- **Тесты:** Go — `go test ./...` в каждом сервисе (фейки портов, без БД/LiveKit). Интеграционный харнес `back-go/apitest` (real Postgres/Redis, сервисы на портах +10000) — сквозные сценарии кросс-сервисных хуков (petsvc↔tasksvc, portalsvc↔messenger), покрытие бэкапа, многокомпанийность, отпуск, лимиты биллинга; aisvc туда намеренно НЕ поднимается (нужен реальный ключ LLM) — проверяется fail-open поведение остальных.
- **Интеграционный стенд ФРОНТА** (`front/tests/integration`, `npx vitest run --project integration`) — второй, независимый: те же Postgres/Redis, но СВОЯ база и блок портов **+10100**, плюс mailpit (письмо-приглашение fail-closed — без SMTP тест невозможен). Поднимает ПЯТНАДЦАТЬ сервисов; не поднимаются только gatewaysvc (WS не нужен REST-сценариям) и nginx. Сценарии ходят **через фронтовые `api/*.js` и сторы**, поэтому ловят дрейф контракта раньше UI; `setup/harness.js` — fetch-шим (маршрутизация `/api/*` по портам, cookie-jar на каждого `Session`, сборка multipart для файловых ручек), `setup/factory.js` — пользователи/компании, `dbQuery` — прямой psql (подготовка данных и проверка того, чего REST не отдаёт). Файлы идут ПОСЛЕДОВАТЕЛЬНО (`fileParallelism: false`) — на этом держится сценарий деструктивного импорта бэкапа. `GW_DUMP_LOGS=1` печатает логи сервисов при завершении. Каталог цен, настройки платформы и прочее ОБЩЕЕ состояние тест обязан возвращать как было — иначе ломает соседние.
  **Правило для этих тестов: подстраивать под бизнес-логику, а не под фактическое поведение кода.** Разошлись — сначала решить, что правильно, и чинить сервер; тест, подогнанный под баг, скрывает именно те ошибки, ради которых написан.
- Если БД не принимает пароль (старый pg_data volume): `docker exec deploy-db-1 psql -U grovework -d grovework -c "ALTER USER grovework WITH PASSWORD 'grovework_local';"`, затем `make dev-migrate`.

## Ветки и релизы

- **`main` — релизная линия: ровно то, что стоит в проде** (`make deploy` на сервере делает `git reset --hard origin/main`). Каждый выпуск помечен тегом `vX.Y.Z`.
- **`develop` — линия следующего выпуска**, вся текущая разработка идёт сюда. `feature/*` — от `develop` и обратно в `develop`.
- **`hotfix/*` — срочная правка прода**: от `main`, ff-merge в `main`, тег; в `develop` заносится отдельно, если правки там ещё нет.
- **`release/*`** — стабилизация выпуска: от `develop`, по готовности в `main` с тегом.
- **Собирать образы и артефакты можно ТОЛЬКО с `main`.** Они собираются из РАБОЧЕГО ДЕРЕВА и уезжают в подвижные теги `<svc>`, которые прод тянет при ближайшем `up`, — то есть `make push` из `develop` протащил бы недоделанную версию в обход веток. Сторожит цель `release-branch` (её требуют `push`, `push-all`, `apk`, `desktop`, `deploy-apk`, `deploy-desktop`, `release`); осознанное исключение — `ALLOW_ANY_BRANCH=1`.
- **Пока `develop` впереди по goose-миграциям, новые миграции в `main` не заводить**: одинаковые номера в двух линиях дадут goose дубль версии. Точечные правки данных на релизной линии — разовым SQL при выкате.

```bash
make backup    # pg_dump прод-БД → backups/gw2_<дата>.sql.gz
make reset NEWPASS='...'  # сброс пароля суперадмина (pgcrypto, без утечки в ps)
make release MSG="..." [V=1.0.6] [BUILD=2607111]  # ПОЛНЫЙ релиз: коммит, автоинкремент versionCode
               # мобилы (ГГММДДН) и версии десктопа, make apk + desktop, докоммит version.json,
               # make deploy + deploy-apk + deploy-desktop
```

**Сервер образы НЕ собирает.** `scripts/build_push.sh` собирает локально под `linux/amd64` (Go-стадии — нативный кросс через `$BUILDPLATFORM`) и пушит в ОДИН репозиторий Docker Hub `osipovskijdima/groove_work` с тегами `<svc>` + версионными `<svc>-X.Y.Z` (версия из `front/package.json`). Go-образы собираются из общего контекста `back-go/` (внутрь копируется и модуль pkg). Пушится только изменившееся (`--changed` по git diff; правка pkg → все Go-сервисы; bind-mount'ы образ не трогают). Откат: в `deploy/.env` на сервере `<SVC>_TAG=<svc>-3.7.0`, затем pull+up.

`scripts/deploy_server.sh` (идемпотентен): 1) синк `deploy/.env` — недостающие секреты генерирует сам (DB_PASSWORD, Fernet-ключи, LIVEKIT_*, пара PASETO Ed25519 целиком + refresh-ключ), существующие НЕ перезаписывает, устаревшие вычищает, бэкапит .env; 2) ufw: 7881/tcp, 7882/udp + 5349/tcp, 3478/udp (TURN) + UDP-буферы ядра (16 МБ, persistent — качество WebRTC под нагрузкой); 3) `pull` + `up -d --no-build --remove-orphans` + prune старых слоёв (миграции применит run-once `migrate`); 4) `nginx -t` + reload (конфиг bind-mounted); 5) health-чеки фронта, `/healthz` всех сервисов, ключевых маршрутов через nginx, `/livekit/`, TCP 7881 и TURN/TLS 5349. `--env-only` — только синк .env. Подробности — `DEPLOY.md`.

**Важно:** правка bind-mounted файла nginx после `git reset` меняет inode — `make deploy` её не подхватит, нужен `up -d --force-recreate --no-deps nginx`. `package-lock.json` регенерировать только в linux-контейнере (macOS-npm теряет optional-deps `@emnapi/*`, и `npm ci` на сервере падает).

## Версионирование

**Единый источник истины на сервере, без хардкода в клиентах:**
- **Версия продукта** = `data/changelog.json` — плоский объект текущего выпуска (`version`, `build`, `date` + пользовательские `title`/`description`/`highlights`). Ключ `version` идёт ПЕРВЫМ: `versionName` Gradle читает его regex-ом. И фронт, и мобильное приложение подтягивают его с сервера (`/api/changelog`, `useAppVersion()`); в бандл версия НЕ зашивается. Отдельного окна истории версий нет — только карточка «Версия · Сборка · Дата выпуска» и «Что нового» в «Настройки → О приложении».
- **Мобильное приложение** = `apps/mobile/version.json` (`current_build`, формат ГГММДДН — versionCode; читает Gradle при `make apk`). Канал `/apps/mobile/`: сюда смотрят карточка «Скачать APK», автопроверка обновлений (раз в 6 часов) и кнопка принудительной проверки (нативный плагин `NativeShellPlugin` — check/download/install + окраска системных панелей под тему). Релиз APK: поднять `current_build` → `make apk` → `make deploy-apk`. Подпись/applicationId неизменны — APK встаёт обновлением поверх.
- **Старый канал** `apps/version.json` + `/apps/groovework.apk` — ЗЕРКАЛО нового APK (пишется автоматически в `make apk`): установленные ранее нативные приложения обновляются по нему до текущей обёртки. Каналы держать синхронными.
- **Десктоп-клиент** = `apps/desktop/version.json` (`current_version` semver из `desktop/package.json` + имена артефактов). Пишется `make desktop`, заливается `make deploy-desktop`. Обёртка сверяет свою версию при старте и раз в 6 часов и предлагает скачать установщик; сам UI приезжает с прод-сервера обычным деплоем. Артефакты обязаны нести версию в имени — иначе обновление копирует старые файлы.

Мини-версии за фиксы одного релиза не плодим. Правила описания выпуска — принцип 11.
